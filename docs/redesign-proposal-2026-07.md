## 1.2 当前路由结构(实际上没有路由)

应用**没有任何 router**。全部导航状态是 `AppShell.tsx` 里的 `useState`:

```text
AppShell
├── activePage: "servers" | "java" | "logger" | "settings"   (useState,不进 URL)
├── selectedServerId: string | null                          (useState,不进 URL)
├── isCreateServerActive + 7 个向导壳状态                     (useState)
└── ServerDetail
    └── activeTab: 23 选 1(zustand persist 到 localStorage,按服务器记忆)
```

后果:无深链、无前进/后退、刷新丢失位置(仅详情标签被 localStorage 记住)、测试与支持沟通("你在哪个页面?")都困难。

## 1.3 功能清单与可达性

- 4 个全局页面:仪表盘、Java Runtimes、Logger、Settings(12 节)。
- 服务器详情 **23 个扁平标签**,由 6 个懒加载容器分发(Activity×5、PlayerLists×4、Settings×8、Content×3、Console、Files、Backups)。
- 创建向导 6 步(来源→兼容性→Java→配置→复核→安装),约 1045 行、~30 个 useState。
- 全局:拖放导入、provisioning 恢复条、关闭行为对话框、右侧上下文栏、底部状态栏。
- 已确认死代码/不可达:`JavaRuntimesView`/`SettingsView` 的 `embedded` prop(仅测试使用);`ProfileImportExport` 无服务器模式(无入口);`ServerContextPane` 的按标签差异化(传入 `activeTab` 但内容从不变化)。

## 1.4 用户角色清单

桌面单机应用,**无多用户/权限体系**。"权限态"在本应用中的实际形态是:
- 运行态门控(服务器运行/停止决定可用操作:Gamerules 需运行、Restore 禁止运行时执行、命令发送需运行)
- 桌面运行时可用性(浏览器/降级模式 vs Electron)
- 协议门控(EULA、Java 许可、非验证包确认)

## 1.5 主要可用性问题(按严重度排序)

1. **23 个扁平标签是 IA 的塌方点**。实测 1100px 宽度下标签条超出可视区 1499px(约 2.5 屏),600px 下达 1751px。功能按实现切分(operators/whitelist/banned-players/banned-ips 是同一个组件的四个入口),不按用户任务切分。
2. **同屏信息三重重复**:详情 Overview 同时渲染 ServerTelemetryStrip(CPU/内存/玩家/TPS)、右侧上下文栏(同一组遥测 + 同一组 Recent Activity)、Overview 面板自身(又一份 Recent Activity)。实测同屏出现 2 份 Recent Activity、2 份完整遥测、3 处状态徽章。
3. **配置表单暴露后端机制**:Updates 标签要求用户手动粘贴"已下载 jar 路径 + SHA-256";Content update policy 要求手动键入"候选更新的名称/当前版本/最新版本/警告"来预演策略。这是把工程内幕直接搬进 UI。
4. **三个玩家表面、三个日志表面**:PlayersView(在线名单+命令动作)/ PlayerListsView(直接编辑 JSON 文件)/ Console 内 ops-whitelist 快捷 Select 三路并行;AppLoggerView / ServerLogsView / 事件时间线(Overview、上下文栏、Console)各自为政。
5. **两个近乎重复的市场浏览器**:`ServerMarketplaceView`(约 670 行)与 `CreateServerMarketplaceBrowser`(约 885 行)各自实现搜索/详情/画廊/版本列表。
6. **错误呈现失控**:InstalledContentView 最多同时堆叠 7 条 mutation 错误横幅;Properties 面板把原始 JS 异常文本直接给用户;Tasks 面板出现 `[[undefined]]`。
7. **保存模型精神分裂**:App Settings 大部分节为逐字段自动保存,Notifications 节却是草稿+显式保存;详情内 General/Properties/Policy 是整表单保存;Gamerules 是即发命令。用户无法建立"我的更改何时生效"的心智模型。
8. **未保存更改仅向导受保护**:Properties/文件编辑器/玩家名单都做了脏值追踪,但切换标签/服务器会静默丢弃;全应用没有任何 `beforeunload` 或导航守卫(向导除外)。
9. **"页中页"**:Network 标签内渲染完整的 Tunnel Providers 独立页面(自带页头/eyebrow/h1),且绑定编辑器只见得到单个服务器。

## 1.6 数据流问题(代码审计实证)

- **N+1 轮询**:侧边栏对每台服务器 `useQueries` 以 1.5s 轮询进程状态,叠加全局 summary 1.5s——N 台服务器时空闲状态每 1.5s 产生 N+1 次 IPC。
- **控制台以 1s 轮询整份事件列表**再在客户端 diff,模拟流式;preload 只有一条 main→renderer 推送通道(close-behavior),**全应用零事件推送**。
- 同一 `serverProcessStatus(id)` 键的 `refetchInterval` 在 6+ 个组件里重复声明(靠查询键去重侥幸避免风暴);`performanceHistory` 每 5s 被最多 3 个组件整份拉取、却只读 `samples[0]`。
- QueryClient 全默认(无 staleTime/gcTime),查询键一半集中注册、一半散落字符串数组(`["performanceHistory", id]` 在 3 个文件重复拼写)。
- 表单零 react-hook-form(依赖装了 `react-hook-form`+`@hookform/resolvers`+`zod` 却未使用);"baseline-ref 防覆写"这段最难写对的逻辑在 3 处独立复制。

## 1.7 组件与样式问题(代码审计实证)

- **两套完整设计系统叠放**:`styles.css`(9273 行,绿色 accent"Discord 风")被 `styles/preview/*`(蓝色"Command Studio",共 3173 行)整体级联覆盖。同名 token 双值(`--radius-sm` 8px vs 6px;两套互不相同的浅色调色板)。约 9000 行事实死代码,改 `styles.css` 无效果——维护陷阱。
- **7 套各自为政的表格实现**(server/backups/java/content/players/structured×2),无共享 Table 组件。
- **4 种对话框构成方式**(DialogSurface / ConfirmDangerDialog / 3 处裸 Radix Dialog)。
- 断点散乱无 token:1280/1180/1120/1100/1000/900/820/760/640/600/480。
- 亮点(应保留):Radix 包装的表单控件统一且质量好;右键菜单键盘支持完整(ContextMenu 键、Shift+F10、焦点还原);reduced-motion 双层处理;i18n 覆盖 en/zh-CN 且有硬编码检查测试。
- 弱点:拖拽分组无键盘替代路径;分组重命名用 `window.prompt`;LoadingState 默认文案未 i18n。

## 1.8 架构约束

- Electron 单通道 IPC,约 130 条命令白名单;`backend.cjs` 单体 6466 行;服务端 SQLite。
- 渲染层完全依赖 `window.mcServerManager`,浏览器模式全量报错(有归一化,但靠字符串匹配错误消息,脆)。
- 桌面为主战场,响应式仅是"窗口变窄的优雅降级"(侧栏 60→52px 图标轨),这个定位对 Electron 是合理的——真正的问题不在移动端,在 900–1200px 的常见窗口宽度下详情页已经塌。

# 二、产品与工作流分析(Product & Workflow Analysis)

## 2.1 产品定位

本地桌面 Minecraft 服务器管理器,**目标用户是想和朋友联机的普通玩家**,兼顾进阶腐竹。近期提交记录("beginner-friendly redesign phase 1/2")与大量 UI 文案("The app explains what is missing; you still choose downloads and agreements yourself")印证:产品哲学是**引导而不代劳**——不替用户接受协议、不替用户选择下载源。重设计必须保留这条产品红线。

## 2.2 用户画像 **[假设,由界面与文案推断]**

| 画像 | 占比预估 | 核心诉求 |
|---|---|---|
| 新手房主 | ~60% | "开个服和朋友玩":创建→启动→让朋友连进来→别崩 |
| 进阶腐竹 | ~30% | 装模组/插件、调 properties、定时备份、看谁在线 |
| 硬核玩家 | ~10% | 文件级编辑、自动化任务、多服、隧道、性能调优 |

## 2.3 任务频率 × 价值矩阵

| 任务 | 频率 | 价值 | 当前成本 |
|---|---|---|---|
| 启动/停止/看状态 | 极高 | 高 | 低(做得好)✅ |
| 发命令/看控制台 | 高 | 高 | 中(控制台不错,但 gamerules 藏在设置组)|
| **让朋友连进来**(端口/隧道)| 高(新手第一目标)| 极高 | **高**(隧道藏在第 20 个标签"Network"里,还是页中页)|
| 管玩家(op/白名单/封禁)| 高 | 高 | **高**(3 个表面、5 个标签)|
| 装/更新模组 | 中 | 高 | 中(市场可用,更新策略页离谱)|
| 备份/恢复 | 中 | 极高 | 中(备份页尚可,入口太深)|
| 创建服务器 | 低 | 极高 | 低(向导是全应用最佳体验)✅ |
| 改 properties/gamerules | 中 | 中 | 中 |
| 崩溃恢复 | 低 | 极高 | 高(线索分散在 Logger/Logs/Diagnostics/Console 四处)|
| 服务器本体升级 | 低 | 中 | **极高**(手贴 jar+SHA-256)|

## 2.4 结构与需求的错配

当前 23 标签把"每个后端域一个标签"平铺,等权呈现;但用户任务集中在 6 个丛:**运行监控、控制台、玩家、内容、数据(文件+备份)、配置**。前 10 个高频任务里有 4 个(联机、玩家、崩溃恢复、升级)被现有 IA 显著劣化。

# 三、三个重设计概念(Three Redesign Concepts)

## 概念 A:「任务中枢」(Mission Control)——任务优先 + 命令面板

**核心哲学**:UI 按用户任务组织而非按数据域组织;高频动作永远一键可达;低频功能进命令面板和渐进披露。

- **导航模型**:顶层仅两级——左侧超窄图标轨(仪表盘/当前服务器/应用设置)+ 全局命令面板(Ctrl+K,承载"创建备份、检查更新、打开文件夹"等全部动词)。
- **页面地图**:仪表盘(全部服务器卡片 + 全局健康)→ 服务器页(单页纵向滚动:状态头 → 快速动作 → 遥测 → 分区卡片,每张卡片"查看全部"进二级页)。
- **仪表盘用途**:健康总览 + 异常聚合(崩溃、待更新、备份过期置顶)。
- **典型流**:装模组 = 服务器页"内容"卡 → 内容二级页;或 Ctrl+K "install mod"。
- **线框(服务器页)**:

```text
┌────────────────────────────────────────────────────────┐
│ ◀ 服务器名  [运行中]  启动|停止|重启  ⌘K 命令面板       │
├────────────────────────────────────────────────────────┤
│ CPU 18% · 内存 2.5G · 玩家 2 · TPS 19.9   [邀请朋友]   │
├──────────────┬──────────────┬──────────────────────────┤
│ 控制台预览    │ 在线玩家(2)  │ 最近事件                  │
│ [打开控制台] │ [管理玩家]   │ [查看日志]                │
├──────────────┴──────────────┴──────────────────────────┤
│ 内容(12 模组,3 可更新)   备份(昨天)   设置          │
└────────────────────────────────────────────────────────┘
```

- **优点**:高频任务成本最低;新手看到的是"我能干什么"而非"系统有什么";命令面板天然可扩展。
- **缺点**:二级页跳转多,进阶用户嫌绕;命令面板对纯鼠标新手有发现性问题;卡片摘要与二级页内容要维护两份呈现。
- **适用**:以新手为绝对主体、功能还会继续膨胀的产品。
- **实现复杂度**:高(几乎所有页面重排 + 新命令面板体系)。
- **风险**:摘要卡设计不好会退化成"到处都是查看全部"。

## 概念 B:「工作台」(Workbench)——实体优先 + 主从布局 + 分区侧导航

**核心哲学**:服务器是一等实体;选中服务器后进入稳定的工作台,**左侧二级导航替换 23 个横向标签**;控制台与监控是常驻工作面。

- **导航模型**:左侧全局栏(服务器列表 + 3 个全局页)保留现状骨架;服务器内部改为**左侧 7 节纵向导航**(总览/控制台/玩家/内容/文件与备份/运行状况/设置),设置节内部再带节内锚点导航。URL 路由化:`#/servers/:id/players` 可深链。
- **仪表盘用途**:多服运营台(表格 + 异常横幅),单服用户几乎直接住在工作台里。
- **典型流**:管玩家 = 选服务器 → 左导航"玩家"→ 段控切换 在线/OP/白名单/封禁(同一数据模型,双写命令与文件)。
- **线框(工作台)**:

```text
┌──────┬──────────┬───────────────────────────────┬─────────┐
│ 全局 │ 服务器内 │ 主工作区                       │ 上下文栏 │
│ 侧栏 │ 二级导航 │                               │ (可关)  │
│ 服务 │ 总览     │  [玩家] 在线|OP|白名单|封禁     │ 遥测     │
│ 器列 │ 控制台   │  ┌─────────────────────────┐  │ 迷你控制 │
│ 表   │ ▸玩家    │  │ 表格:玩家/状态/动作      │  │ 台       │
│      │ 内容     │  └─────────────────────────┘  │ 事件     │
│ Java │ 文件备份 │                               │         │
│ 设置 │ 运行状况 │                               │         │
│      │ 设置     │                               │         │
└──────┴──────────┴───────────────────────────────┴─────────┘
```

- **优点**:结构变化最小却根治标签溢出;二级导航天然容纳分组与徽标(如"3 可更新");窄窗口下二级导航可折叠为图标;与现有代码(6 个容器组件)映射干净,迁移成本最低。
- **缺点**:双侧栏在 900px 以下要精心折叠;"仪表盘"对单服用户价值有限;不如 A 激进,任务发现仍靠名词导航。
- **适用**:桌面为主、用户会长时间驻留单服工作台的场景——即本产品。
- **实现复杂度**:中。
- **风险**:上下文栏若不砍掉重复信息,双侧栏更挤。

## 概念 C:「家用主机」(Appliance)——引导优先 + 大卡片 + 模式开关

**核心哲学**:像游戏主机系统设置一样:大卡片、每次一个决定、全部配置走引导流;"高级模式"全局开关解锁密度。

- **导航模型**:无侧栏。首页即服务器大卡片墙;进入服务器后是 4 个大按钮(玩、人、物、修);一切复杂表单改为分步引导(如"升级服务器"是 3 步向导);高级模式开启后出现文件/属性/诊断入口。
- **仪表盘用途**:卡片墙,每卡自带启动按钮和"邀请朋友"。
- **线框(服务器首页)**:

```text
┌────────────────────────────────────────────┐
│  Fabric Workshop            [■ 停止] 运行中 │
│  2 名玩家在线 · 一切正常 ✓                  │
├─────────────┬─────────────┬────────────────┤
│  🎮 游玩     │ 👥 玩家      │  📦 模组        │
│  控制台/命令 │ 邀请/OP/封禁 │  安装/更新      │
├─────────────┴─────────────┴────────────────┤
│  🛡 维护:备份 · 升级 · 体检   [高级模式 ⚙] │
└────────────────────────────────────────────┘
```

- **优点**:新手零学习成本;把"邀请朋友"提到一级;引导流天然防错。
- **缺点**:进阶用户操作成本大增(一切都是向导);与现有信息密度差距太大,迁移是重写;高级模式开关造成两套 UI 的长期维护税。
- **适用**:定位纯消费级、放弃硬核用户时。
- **实现复杂度**:极高(重写)。
- **风险**:最高;且与现有"表格+表单"资产几乎零复用。

# 四、推荐方向(Recommended Direction)

## 4.1 选择:**概念 B 为骨架,吸收 A 与 C 的关键器官**

- 取 B 的:服务器工作台 + 左侧 7 节二级导航 + URL 路由 + 主从骨架(迁移成本最低、根治标签塌方)。
- 取 A 的:①"邀请朋友"提为一级动作(状态头常驻按钮,聚合端口/局域网/隧道);②异常聚合仪表盘(崩溃/可更新/备份过期置顶);③命令面板 Ctrl+K 作为 P2 增强(非首期)。
- 取 C 的:①所有危险/复杂操作走分步引导(服务器升级、恢复备份、策略设置);②"基础/高级"披露原则——但用**节内渐进披露**(Advanced 折叠区)而非全局模式开关,避免双 UI 维护税。

## 4.2 为什么不是 A 或 C

- A 的收益(任务发现)可以由 B+徽标+命令面板逐步获得,而 A 的成本(全量重排 + 摘要卡双呈现)一次性全付。
- C 与现存代码资产(表格、表单、控制台)复用率过低,等于重写,且抛弃了 30–40% 的进阶用户。

## 4.3 主要风险与权衡

| 风险 | 缓解 |
|---|---|
| 双侧栏挤压窄窗口 | ≤1100px 二级导航折叠为 52px 图标轨;≤880px 全局侧栏自动收起;上下文栏默认关闭仅控制台开 |
| 引入路由触碰所有导航代码 | 阶段 2 单独落地,router 先镜像现有 state 再逐页切换 |
| 玩家双写(命令+文件)有一致性坑 | 后端提供统一 `players` 域命令(见 §8.7),UI 不再关心写入路径 |
| 删除 9273 行旧 CSS 可能有隐性依赖 | 阶段 1 先做 token 快照对比测试,再删除 |

# 七、核心用户流(Core User Flows)

> 步数 = 用户可感知的点击/输入决策点。

## 7.1 创建并启动第一台服务器
- **现**:仪表盘→创建→(6 步向导)→完成回仪表盘→找到行→启动。约 10–12 步。
- **新**:同向导(默认折叠高级组,步 3 决策点 -4)→完成页直接 [启动并打开工作台]。约 7–8 步,**-3 步**;失败态:安装失败=step5 重试/放弃(保留),启动失败=映射指导(保留 startFailureGuide)。

## 7.2 让朋友连进来(新手价值最高流)
- **现**:无引导。用户需自行发现 Network 标签(第 20 个,需横向滚动)→理解"隧道供应商"概念→配置→绑定→启动;或自己去查端口转发。≥ 10 步 + 大量场外知识。
- **新**:状态头 [邀请朋友] → 弹层:本机地址即拷、公网说明、隧道一键启动或"配置(2 步引导)"。**3–5 步**;失败态:隧道进程退出→弹层内错误+重试;权限/防火墙问题→说明文案。

## 7.3 给在线玩家封禁/加白
- **现**:5 步(横向滚动找标签、双表面混淆)。
- **新**:3 步(玩家→行内动作→确认);运行/停止两态由后端统一处理,UI 无差别。

## 7.4 装模组
- **现**:Content→(另一个标签)Marketplace→搜索→选版本→安装→回 Content 确认。6–7 步,标签间穿梭。
- **新**:内容→[浏览内容]全屏→搜索→详情→安装(乐观行内进度)→自动回已安装并高亮新行。5 步,无穿梭;失败=安装行内错误+重试。

## 7.5 崩溃恢复
- **现**:仪表盘红数字(不可点)→进服→自己在 Console/Logs/Diagnostics/Logger 四处找线索。
- **新**:仪表盘异常条 [1 台崩溃] →直达 运行状况·体检,页内聚合:最后 50 行日志 + 崩溃事件 + [运行体检] + [重启];**-4 步**且路径确定。

## 7.6 升级服务器版本
- **现**:Updates 标签手贴 jar 路径+SHA-256,4 字段裸表单,无备份提示。
- **新**:设置·版本升级 3 步引导:检查(自动)→提供 jar(带"从哪下载"说明链接,保留用户自选红线)→**强制备份提示**+安装;失败=保留原状+错误说明。步数持平但决策防错质变。

## 7.7 备份与恢复
- **现**:备份尚可;恢复=表格行内表单+确认。
- **新**:恢复 2 步引导(选位置→带后果清单确认);运行中禁用逻辑保留;恢复完成通知铃铛+事件时间线记录。

# 八、数据与状态架构(Data & State Architecture)

## 8.1 状态归属总表

| 状态 | 现在 | 目标 |
|---|---|---|
| 当前页/选中服务器/节内视图/文件路径/市场搜索 | useState 或丢失 | **URL(hash router)** |
| 服务器列表、状态、遥测、事件、内容、备份… | React Query(键半集中)| React Query,**键全集中 + 分层**(`['server', id, 'status']`)|
| 详情活跃节 | localStorage(zustand)| URL;localStorage 仅记"上次访问的服务器" |
| 侧栏折叠/分组/排序 | zustand persist | 保留(纯 UI 偏好)|
| 表单草稿 | 手写 useState + baselineRef ×3 | **react-hook-form + zod**(依赖已装),`useUnsavedGuard` 统一守卫 |
| 主题/语言 | i18n context + localStorage | 保留;键名统一 `mcsm.*` 并加版本号 |
| 通知/瞬态错误 | 各组件横幅 | 全局 `notificationStore`(zustand,非持久)+ 铃铛面板 |

## 8.2 查询键规范

```ts
// src/lib/queryKeys.ts —— 唯一出处,禁止内联字符串键
server = {
  all: ['servers'],
  profile: (id) => ['servers', id],
  status: (id) => ['servers', id, 'status'],
  events: (id) => ['servers', id, 'events'],
  performance: (id) => ['servers', id, 'performance'],
  players: (id, view) => ['servers', id, 'players', view], …
}
```
失效走前缀:`invalidateQueries({queryKey: ['servers', id]})` 一次收敛现在 17 处手工逐键失效。

## 8.3 轮询收敛(先做,不依赖后端改造)

- 全局仅**两个**轮询源:`processSummary`(仪表盘可见时 2s)与 `serverStatus(activeId)`(工作台 2s)。侧边栏 N+1 轮询删除——状态点由 summary 携带每服状态(后端 summary 已知全部进程,扩展返回 `perServer: {id: status}`,一次 IPC 替代 N 次)。
- `refetchInterval` 只允许出现在 `src/lib/polling.ts` 导出的 hook 里;组件一律订阅共享键。
- QueryClient 全局 `staleTime: 5s`(状态类)/`60s`(档案类),消除焦点重复抓取。

## 8.4 推送化(第二步,后端小改)

preload 增加一条事件通道 `server-event`:`{serverId, kind: 'console'|'lifecycle'|'metrics', payload}`。渲染层单例订阅,写入 query cache(`setQueryData` 追加环形缓冲)。控制台 1s 整表轮询、事件 10s 轮询、遥测 5s 轮询全部退役;轮询仅剩离线兜底。这是**唯一必须的后端配合项**,`backend.cjs` 已在进程管道处持有全部事件源。

## 8.5 变更(mutation)规范

- 启停/重启:乐观更新状态徽章 → 事件推送校正。
- 表单保存:成功后 `setQueryData` 直写 + 前缀失效;"需重启"由后端在响应中返回 `restartRequired: string[]`,UI 统一横幅,删除三处手写 diff 判断。
- 错误:mutation 错误一律进通知中心(可展开详情),表单内仅显示字段级校验错;禁止叠横幅。

## 8.6 表单与未保存守卫

`useServerForm(schema, baseline)`:react-hook-form + zodResolver;`formState.isDirty` 驱动粘性操作条;路由 `beforeLeave` + `beforeunload` 统一拦截(替换三份手写 baselineRef 逻辑与向导的专用拦截)。

## 8.7 需要的后端/API 变更(UX 受限点)

| 变更 | 动机 | 规模 |
|---|---|---|
| `get_process_summary` 返回 perServer 状态 | 杀 N+1 轮询 | 小 |
| `server-event` IPC 推送通道 | 控制台/遥测/事件实时化 | 中 |
| 统一玩家域命令 `apply_player_change`(自动选 命令/文件 路径)| 玩家三表面合一 | 中 |
| `get_attention_items`(崩溃/可更新/备份过期聚合)| 仪表盘异常条 | 小 |
| `read_server_properties` 返回带类型/分组/默认值的 schema | 属性页分组+校验+修崩溃 | 中 |
| 更新检查返回结构化结果(替代手输候选)| 更新偏好卡 | 小 |
| 命令注册表按域拆文件(backend.cjs 6466 行)| 可维护性(不阻塞 UI)| 大,可后置 |

# 九、视觉方向(Visual Design Directions)

> 前提:先解决"两套 CSS 叠放"的事实——**无论选哪个方向,第一步都是把 token 收敛为单一来源**。以下三个方向都基于收敛后的 token 层。

## 方向 V1:「指挥舱」Command Deck(推荐)
现行 preview 层("Command Studio" 蓝)的正规化延续,迁移成本最低。
- **气质**:冷静、专业、低噪;深蓝黑基底 `#111823`,蓝 accent `#3478f6`。
- **字体**:UI 用系统栈 sans;数据/控制台用 Cascadia Code;类型阶梯 12/13/14/16/20/24。

- **背景**:纯色分层(app < sidebar < panel < elevated),无渐变无纹理。

- **图标**:lucide 线性(现有),粗细 2,尺寸 13/15/17。

- **复杂界面可读性**:靠"每屏一个主面板 + 卡片分区 + 12 栏网格",不靠颜色区分区域。

## 方向 V2:「工坊」Cozy Craft
- **气质**:温暖友好,向 Minecraft 世界观轻微致意(草方块绿 accent `#5cb85c`、羊皮纸浅色主题、极克制的像素点缀仅用于空态插画)。字体更圆润(Inter),圆角加大(8/12/16/20),卡片带柔和阴影。密度单档偏舒适。适合全力押注新手市场;风险:进阶界面(控制台/表格)与"可爱"气质打架,深色模式下暖色难调。

## 方向 V3:「极简终端」Terminal Minimal
- **气质**:高对比、单色+单 accent(荧光绿或琥珀)、等宽字体占比更高、零圆角或 2px、密度紧凑单档。信息效率最高,气质硬核;对新手威慑力强,与"beginner-friendly"路线冲突。适合 power-user 分叉产品,不推荐主线。

**推荐 V1**:与现行实际渲染层连续(用户无断裂感)、与概念 B 的密度需求匹配、浅色主题已有基础。V2 的空态插画语言可选择性吸收(空态/完成页插画用轻像素风)。

- **缩放/长文本**:zh/en 双语按钮不定宽;200% 缩放下工作台头允许两行换行(实测现在 116px 头部有余量)。
- **破坏性动作**:统一走 ConfirmDialog(打字确认仅限删除服务器/清日志级别);全部可在事件时间线追溯。
- **i18n**:硬编码检查测试保留;新增"缺键即 CI 失败"(杜绝 `[[undefined]]` 上屏)。
